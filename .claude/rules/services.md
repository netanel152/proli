# Service layer (`app/services/`) and the provider facade (`app/providers/whatsapp/`)

Loaded when a file under `app/services/` or `app/providers/` is read. The narrative
version is `docs/ARCHITECTURE.md`; the prescriptive one is `docs/ARCHITECTURE_STANDARD.md`.
The three-process overview and the data layer stay in `CLAUDE.md`.

Two rules from `CLAUDE.md` bind every file here and are repeated because they are the
ones an edit in this directory can break: **every WhatsApp menu is text-only** (nothing
calls `send_interactive`), and **all outbound traffic goes through `app/providers/whatsapp/`**
— no `httpx`/`requests` import under `app/services/` (allowlist: `geocoding_service.py`),
no `CloudAPIProvider(`/`DryRunProvider(` construction outside the facade package. CI greps
for both.

`customer_flow.py`, `pro_flow.py` and the guard chain receive their collaborators (`whatsapp`,
`lead_manager`, `state_manager`, …) **as parameters** — `workflow_service.py` passes its shared
instances — so a flow function is testable against fakes without monkeypatching. Helpers that
still live in `workflow_service` are resolved per call through the module, never imported at
module top, because the suite monkeypatches them late.

### Service Layer (`app/services/`)

| Service | Responsibility |
|---|---|
| `workflow_service.py` | Central orchestrator — builds the per-turn `DispatchContext`/`GuardDeps`, runs `dispatch_guards.GUARD_CHAIN` (PRO-179/PRO-180/PRO-181, slices A1–A3 of the PRO-139 decomposition), then delegates whatever the chain didn't handle to `conversation_pipeline.run_customer_pipeline` (PRO-182, slice B); still owns the collaborator helpers (`_build_pro_response`, `_finalize_deal`, the loyalty-offer and emergency-escalation helpers) that the chain and the pipeline call by name |
| `dispatch_guards.py` | Ordered guard chain (`GUARD_CHAIN`, a tuple — order is load-bearing) for the first 25 branches of dispatch, through the holding-state cluster and the pro-routing cluster: admin routing wizard, global reset, help/menu, inbound rate limit, zero-touch intent confirmation, consent gate, politeness, customer status pull, SOS/human handoff, emergency hoist (PRO-121), pro-approval soft hold, paused-for-human, cancel confirmation, reschedule selection, loyalty confirmation, new-or-existing, the BOOKED cancel/reschedule interceptor (PRO-179/PRO-180), customer-mode switch, pro business-keyword bypass, pro-mode routing, pro onboarding, awaiting address, pro registration keyword, pro autodetect, and the PENDING_ADMIN_REVIEW short-circuit (PRO-181) |
| `conversation_pipeline.py` | `run_customer_pipeline(ctx, deps)` — everything a message reaches once no guard in `GUARD_CHAIN` handles it (PRO-182, PRO-139 slice B): the inbound log, the completion/rating/review branch, media fetch, the active-lead lookup, the PRO-116 Q3 BOOKED gate, the fresh-start context clear, the assigned-pro fast path, the Smart Dispatcher phase, the sticky persistence gate, PRO-119 address-parts persistence, the loyalty check, the matching gate, response selection, and `[DEAL]` detection/finalize. Collaborators are resolved per call in the prologue — never at import — so late monkeypatching of `workflow_service` still works |
| `customer_flow.py` | Customer completion checks (capped + cooled-down per booking — `reassign_lead` clears the counters on a fresh owner, PRO-45; `"2"`/`עדיין לא` acknowledges and restarts the cooldown instead of falling through to the AI; `"3"`/no-show phrasing → `_handle_no_show_report`, PRO-45 and the only production writer of `no_show_count` — atomically claims the BOOKED lead within `NO_SHOW_REPORT_MAX_AGE_HOURS` of the check (or, for written phrasing, once the appointment is due), records the no-show, releases the slot, notifies the pro, pages the operator, and hands off to `monitor_service.reassign_lead(lead, notify_old_pro=False)`); ratings via a tolerant free-text `parse_rating` (digits, Hebrew number words, stars, "X מתוך 5") with a bounded re-prompt (`MAX_RATING_REPROMPTS`) on an unreadable reply and a 48h liveness window (`RATING_PROMPT_MAX_AGE_HOURS`) on the prompt itself (PRO-122); reviews, including an explicit skip path (`Messages.Keywords.SKIP_TOKENS`) that keeps the numeric rating but drops the comment; and rescheduling (writes both `appointment_time` and `appointment_datetime` on a new slot, PRO-45) |
| `pro_flow.py` | Professional text commands (approve, reject, pause, resume, finish, cancel booked job, details, summary, **מצא** — rate-limited stuck-lead search) — implements Dynamic Dashboard and availability controls, rendered (both the dashboard's contextual subset and `Pro.HELP_MENU`'s full list) from the single canonical `Pro.CMD_*` row set (PRO-168) so the two menus cannot advertise different keywords; **עדיין עובד** silences the finish-reminder counters on all of that pro's BOOKED leads without closing any of them; on finish, captures an optional **final_price** (PRO-33) via a non-blocking `PRO_AWAITING_FINAL_PRICE` prompt and derives `commission_amount`; on reject (PRO-117), atomically claims the lead (`rejected_by`/`last_rejected_at`, `expected_status=NEW`) then hands off to `monitor_service.reassign_lead(lead, notify_old_pro=False)` for an automatic rematch — never a dead end — falling back to `_escalate_rejected_lead` (PENDING_ADMIN_REVIEW + admin page + customer message) if the rematch fails or finds no replacement; **מצא**'s claim of a PENDING_ADMIN_REVIEW lead also re-arms `no_show_reported_at` for the claiming pro (PRO-45); **עבודות**/**פרטים** and the **סיימתי**/**ביטול** selection prompts render chronologically by appointment time, grouped by day, and page at `WorkerConstants.PRO_LIST_PAGE_SIZE` rows via `agenda_service` (PRO-147) |
| `agenda_service.py` | Pure formatting for every pro-facing job list — chronological ordering by `appointment_datetime` (unscheduled leads last, under their own header), absolute Israel-time rendering ("היום 14:30" / "מחר 09:00" / "ראשון 3.9 11:00"), bold per-day headers, and pagination (`render_page`); no DB access — callers fetch, this module sorts and renders (PRO-147) |
| `admin_flow.py` | Admin routing wizard (`ניהול` keyword): list PENDING_ADMIN_REVIEW leads → self-assign or pick a pro. The assignment itself lives in the public `assign_lead_to_pro(lead_id, pro, whatsapp, expected_status=None)` (PRO-188) — extracted out of the wizard so the admin panel's one-click assignment strip (`admin_panel/core/assignment.py`) runs the same code instead of a second copy; it re-arms `no_show_reported_at` for the newly-assigned pro alongside `escalation_reason`/`admin_reported_at` (PRO-45), notifies the pro via `notification_service.notify_pro_new_lead`, and returns tri-state offer feedback — sent / didn't reach the pro (assignment stands, contact manually) / post-write lead lookup missed — plus a `LEAD_ALREADY_TAKEN` sentinel when a caller-supplied `expected_status` guard no longer matches; the customer is only told a pro was found once the offer actually reached the pro. The wizard itself (`_assign_lead_to_pro`) is now a thin wrapper that clears wizard state and answers the admin in chat |
| `media_handler.py` | Media type detection and download (images, audio, video) |
| `ai_engine_service.py` | Gemini with adaptive fallback (Flash Lite 3.1 → Flash 3.5 → Flash 2.5 → Flash 1.5); multimodal; 5-turn context window; non-blocking token accounting |
| `matching_service.py` | Progressive `$geoNear` aggregation (10 km → 20 km → 30 km); falls back to regex city match; load-balances by max 3 active leads per pro; `candidate_score`'s no-show penalty is live since PRO-45 (`no_show_count`, written only by `customer_flow._handle_no_show_report`); `is_pro_eligible_for_lead` also excludes the pro named on a lead's `no_show_reported_at`, so they cannot reclaim it via `מצא` — a pro's `$geoNear` eligibility rests entirely on the `location` written by the geocode check below, so a pro with no resolvable area is invisible to matching, not merely deprioritized; the base eligibility clause (`is_active`/`role`/`pending_approval`) is the shared module constant `APPROVED_PRO_FILTER` (PRO-188), reused by the admin panel's one-click assignment strip so it can't build its own pro list and quietly re-admit an inactive or still-queued-for-approval pro, as it did once |
| `geocoding_service.py` | Static dict → Redis cache → Google Geocoding pipeline behind `resolve_city_to_coords`; the status-bearing `geocode()`/`resolve_service_areas(_sync)` (PRO-27) additionally drive the admin-panel Approve-button check that geocodes a pro's `service_areas` and writes their GeoJSON `location`, blocking Approve on a definitive miss (correction box) but never on a geocoder outage (flags `service_areas_geocode_pending` instead); `scripts/check_pro_service_areas.py` runs the same check as a backfill/audit over already-approved pros |
| `state_manager_service.py` | Redis-backed FSM per `chat_id` (`UserStates` enum); supports custom TTL per state |
| `context_manager_service.py` | Stores last 20 messages per `chat_id` in Redis |
| `lead_manager_service.py` | CRUD for leads in MongoDB |
| `notification_service.py` | Sends WhatsApp notifications to pros; SOS alerts; on-call paging via `send_oncall_alert` (WhatsApp when the instance is authorized, else `page_critical` → Sentry/email page); owns the shared lead-offer builder — `build_new_lead_message` (pure) and `notify_pro_new_lead` (sends offer + navigation link, fail-open) — used by `monitor_service`'s reassignment path and `admin_flow`'s assignment path so the message and its media/Hebrew-fallback policy can't drift between callers |
| `monitor_service.py` | Stale job detection, reassignment (shared `reassign_lead` helper — escalates to PENDING_ADMIN_REVIEW, with an immediate admin alert, once `MAX_REASSIGNMENTS` is exhausted; PRO-63, never closes the lead; notifies the new pro via `notification_service.notify_pro_new_lead`, and escalates to PENDING_ADMIN_REVIEW with `escalation_reason: "pro_offer_send_failed"` plus an operator page if that offer doesn't reach the pro (closed 24h window / breaker / raised send) instead of reporting a false success to the customer;
